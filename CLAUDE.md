# Glance

A wall-mounted e-paper dashboard for home, showing weather and public transport departures. The display is a Seeed reTerminal E1001; a small server renders the whole screen as an image and the device just downloads and shows it.

## Hardware

Setup-specific details (hostnames, addresses, user names, which stops and where) are in `CLAUDE.local.md` (git-ignored) and the git-ignored local config files, not here, so this file can be shared.

- **Display:** Seeed reTerminal E1001: ESP32-S3, 7.5" e-paper, 800×480, 4-level greyscale (0, 85, 170, 255), physical buttons, battery powered. Runs this project's own firmware (`glance-device/`, flashed 2026-11-10) in place of Seeed's stock SenseCraft firmware, which Seeed's web flasher can restore.
- **Server:** a Raspberry Pi 1 Model B (ARMv6, one 700 MHz core, little RAM and disk), Raspbian 13 (Trixie), Python 3.13, reached over SSH with key login (`sudo` asks for a password); hostname, address and user are in `CLAUDE.local.md`. Deployed there 2026-11-10. Development happens on the Mac, with tools from mise: each of `glance-server/` and `glance-device/` has its own `mise.toml` (no root one since 2026-11-10). The user's global gitignore ignores `mise.toml`, which kept both out of the first commit; they are tracked now, and the repo's `.gitignore` has `!mise.toml` so new ones aren't missed. Keep dependencies minimal (only Pillow, from Debian's `python3-pil`; piwheels' Pillow wheel needs system libraries the Pi doesn't have). It's slow: drawing one image takes ~2.2 s there (FreeType text rendering dominates), hence the pre-rendering below. From the Mac, the Pi's `.local` name must be reached over IPv4 (`ssh -4`); IPv6 gives "No route to host".
- **Location:** Helsinki, so HSL public transport and FMI weather.

## Architecture (decided)

Server-rendered: the server fetches all data, renders an 800×480 PNG snapped to the four grey levels, and serves it over HTTP on the home network. The device wakes, fetches `/glance.g2` (the same image in the panel's own 2-bit format; `/glance.png` is for browsers), draws it, sleeps. This keeps firmware trivial and battery use low.

SenseCraft's own data-source feature was ruled out: it only handles simple JSON GETs, so FMI (XML) and HSL (GraphQL + API key) don't work.

Pull only, no push (decided 2026-11-10): the device runs on battery and is on USB only while charging, and a deep-sleeping ESP32 can't receive anything, so push or long polling would mean keeping Wi-Fi on. The image is rendered per request, so on-screen minutes are off by at most the wake interval; the wake interval (battery life vs. accuracy) gets settled in the firmware step.

The server decides the wake schedule. Each `/glance.png` and `/glance.g2` response has an `X-Glance-Sleep: <seconds>` header aiming `wake_offset_seconds` (2) after the next wake minute. Wake minutes come from `[[device.schedule]]` rules in `config.toml` (`glance/schedule.py`: `WakeRule`, `WakeSchedule`; first matching rule wins, `days` of the moment itself, `to` exclusive, may run past midnight; otherwise `wake_interval_minutes`); a minute is a wake if it's a multiple of its own rule's interval since midnight, so period starts off the previous interval's grid (e.g. 06:40 after 15-minute nights) are hit exactly. The real schedule lives in `glance-server/config.local.toml` (it reveals the user's routine; details in `CLAUDE.local.md`); `config.toml` has a generic example (weekday mornings 07:00–09:00 every minute, nights 23:00–06:00 every 15 min, otherwise every 5). In periods over 1 minute, departures show clock times (14.32) instead of minutes (`Scene.departure_clock`), since countdowns would go stale. Departures are polled (and the image drawn in advance) only 15 s before wake minutes; other requests (the browser preview, a late device) refetch departures if they're over 60 s old. A request shortly before a wake minute is drawn for that minute: the device's sleep timer runs ~1 % fast (3 s early after 5 min), so the margin is 3 % of the interval that ends at the wake, at least 10 s. All stepping and subtracting of times in `schedule.py` goes through UTC (`_step`, `seconds_between`), so both clock changes work: wall-clock arithmetic lost which pass of the repeated autumn hour a time was in, which put the next wake an hour in the past and told the device to sleep 1 s (fixed 2026-11-11, tested for 2027-10-31). A button press on the device requests `?refresh=1`: that refetches departures first (at most every 10 s). Departure fetches run one at a time; a refresh that arrives during a fetch waits for it and uses its result. Requests wait at most 4 s for departures (`UPSTREAM_WAIT`), then draw with the last good ones while the fetch carries on in the background: the device gives up after 10 s, and upstream timeouts (Digitransit 8 s, FMI 10 s) used to be longer than that. Weather is fetched only by the refresher thread, never in a request. The `X-Glance-Sleep` sent is the planned sleep minus the time the request spent waiting and drawing, because the device counts from when the answer arrives (before 2026-11-11 the wake after an on-demand image came 2.5–9 s late). Ideas not done: hide departures that leave before the next wake.

## Current code (`glance-server/`)

Rebuilt from scratch on 2026-11-09 (the original sandbox code was lost).

- `glance/fmi.py`: FMI open data WFS client (stored query `fmi::forecast::edited::weather::scandinavia::point::simple`, params Temperature, WindSpeedMS, WindDirection, PoP, WeatherSymbol3, FeelsLike, hourly). No API key. Parses the "simple" XML with stdlib ElementTree; `NaN` values become `None`; an `ExceptionReport` raises `FMIError`. Fetches from local midnight to now + 36 h so today's high/low covers the whole day (FMI returns past hours of the edited forecast). Maps WeatherSymbol3 codes to icon kind, intensity and Finnish/English descriptions. JSON cache (`cache/forecast.json`) for fallback; it records the parameters it was fetched with, and a cache missing a newly added parameter is refetched at startup instead of waiting out the 15 min. **Verified against the live API**; `tests/data/fmi_simple.xml` is a real response.
- `glance/render.py`: grid, widgets, text fitting, final quantisation to 4 greys. `glance/icons.py`: weather icons are FMI's own WeatherSymbol3 symbols (chosen with the user 2026-11-10), loaded from pre-rendered PNGs in `icons/fmi/76/` (current weather) and `icons/fmi/36/` (hourly); our earlier hand-drawn icons (`icons.draw`, 4× supersampled) remain only as the fallback for a code without a PNG, and the wind arrow is drawn there. `glance/i18n.py`: en/fi strings and date/time formats (Finnish uses `22.47`).
- `glance/departures.py`: `Departure` (absolute departure `time`; minutes are computed at render time, so cached data keeps counting down correctly) and `StopDepartures`, plus placeholder data.
- `glance/hsl.py`: Digitransit routing API v2 client (`https://api.digitransit.fi/routing/v2/hsl/gtfs/v1`, key in the `digitransit-subscription-key` header). One request for all stops: `stops(ids:)` → `stoptimesWithoutPatterns` (omits cancelled trips and drop-off-only stops). Departure time = `serviceDay + realtimeDeparture`. A widget can merge several stops (e.g. both platforms) and filter to listed routes. Stops are configured by their sign codes (`H0665`): the routing API's stop search matches names only, so codes are resolved to gtfsIds through the geocoding API (`/geocoding/v1/search`, source `gtfshsl`, exact `addendum.GTFS.code` match) once and cached in `cache/stop_codes.json`. **Verified against the live API** on 2026-11-09; `tests/data/hsl_departures.json` is a real response. HSL headsigns' " via …" part is dropped ("Herttoniemi(M) via Kalasatama(M)" → "Herttoniemi(M)"; decided with the user 2026-11-09) so destinations fit. Trunk routes are recognised by GTFS route type 702 (`route.type`; 701 = city bus, 700 = regional, both blue at HSL); the API's colour fields are empty.
- `glance/__main__.py`: `python -m glance render [-o file] [--offline]` writes a PNG; `python -m glance serve [--port N]` serves `/glance.png` (rendered per request) plus a browser preview at `/`; `python -m glance stops "Pasila"` lists matching stop codes and the routes/headsigns serving them. `--lang fi` overrides the language; `-v` also logs every departures fetch. A background thread refreshes weather at most every 15 min and departures just before every minute (see the wake schedule above; logic in `glance/schedule.py`). The browser preview behaves like the device: it follows `X-Glance-Sleep` and has a button that sends `?refresh=1`.
- Failure handling: the last good data is kept. `Weather.refresh` and `Transit.refresh` never raise: every way a fetch can fail (error pages that aren't XML, bodies cut short, JSON of the wrong shape, an unwritable cache) becomes `FMIError`/`HSLError` or is caught and logged, and the refresher loop guards each round as well. Before 2026-11-11 one such response ended the refresher thread for good while the process lived on, with no polling, no pre-drawn images and nothing to restart it. A stop code that HSL doesn't know is looked up once per run, not at every poll; a cached id that HSL no longer knows (a renumbered stop) is looked up again once per run. A failed weather fetch is retried after 2 minutes, not the full 15. Infinite values from FMI are dropped like NaN (from the cache too): they can't be drawn. If no thread can be started for a request's departures fetch, the request is drawn with the last good data. The status bar's right side is empty while data is fresh; when weather is over 45 min old or departures over 5 min old, it shows an inverted warning badge ("Weather 2 h old", "Departures 12 min old"), and stale realtime minutes are drawn dark grey like scheduled ones. Without a key, or for a stop without codes, placeholder departures are shown.
- `config.toml`: language (`en`/`fi`), timezone, coordinates (placeholder: Pasila), server host/port (and `hostnames`, extra names the server may be called by; see Security), weather refresh/staleness, departure polling (`poll_lead_seconds`, `min_refresh_seconds`) and staleness, device wake schedule (`[device]`, `[[device.schedule]]`), stops (`codes` like `H0665` or `ids` like `HSL:1174411`, optional `routes`, optional `name`, which defaults to HSL's stop name, fetched with the departures). `config.local.toml` (git-ignored) overrides it (sections merge, lists like `[[stops]]` are replaced whole): the Digitransit key, the real `[location]` and the real `[[stops]]` go there, while `config.toml` keeps Pasila examples (moved 2026-11-10 so the shareable files don't reveal where the user lives) as `[digitransit] key = "..."`, or in the `GLANCE_DIGITRANSIT_KEY` environment variable.
- Fonts: bundled Inter 4.1 static TTFs in `fonts/` (OFL licence in `fonts/LICENSE.txt`).
- Weather icons: from [fmidev/opendata-resources](https://github.com/fmidev/opendata-resources) `symbols/WeatherSymbol3` (MIT; notice in `icons/fmi/LICENSE`, keep it with the icons). The originals are coloured with hairline outlines, so `tools/build_fmi_icons.py` adapts them for 4-grey e-paper: thicker cloud outlines (more for the small size), a light-grey sun with a black outline, black lightning (FMI draws it in the sun's yellow; told apart by drawing order: sun before the cloud, lightning after), black thickened snowflakes, dark-grey raindrops (black at 36 px; drop vs. flake told apart by path length), and a shared crop of FMI's wide margins. It renders the SVGs with macOS Quick Look (`qlmanage`; always at 304 px, since smaller thumbnails come out at the wrong scale; ImageMagick's built-in SVG renderer loses the cloud outlines) and writes PNGs, which are committed, so the Pi never renders SVG. Mac-only; rerun it only to change the icons. Stripped source SVGs are in `icons/fmi/src/`.
- Mode icons in stop headers (added 2026-11-10 with the user): HSL's own pictograms (tram, bus, subway, rail, ferry) from [HSLdevcom/digitransit-ui](https://github.com/HSLdevcom/digitransit-ui) `app/assets/icons/default/icon_*.svg`, dual-licensed **EUPL 1.2 / AGPLv3** (copyleft, unlike FMI's MIT): `icons/hsl/COPYING`, `LICENSE-EUPL.txt` and `README` must stay with them, and if the project is ever published those files keep that licence. They're single-colour, so `tools/build_hsl_icons.py` only crops and scales them to 28 px (`icons/hsl/28/`; enlarged from 22 px with the user; 28 px is about the most the header fits without moving the departure rows down). Each stop's mode comes from the HSL API (`vehicleMode`, fetched with the departures), so a stop with no departures still gets its icon; a widget merging stops of several modes shows one icon per mode (order: subway, rail, tram, bus, ferry). Both icon scripts share `tools/svg_render.py` (Quick Look rendering, cropping).
- Pre-rendering (`schedule.Prerendered`): right after the poll 15 s before each minute, the server draws the coming minute's image and serves it to requests up to 20 s into that minute (the device's wake), in ~45 ms on the Pi. Later requests and `?refresh=1` are drawn fresh (~2.5 s). PNGs use `compress_level=6` (0.16 s on the Pi vs 1.1 s for `optimize=True`, ~6 % bigger).
- `deploy/`: `deploy.sh user@host` rsyncs the code to `~/glance-server` (not `.venv`, `cache`), copies `config.local.toml` with mode 600, makes a venv with `--system-site-packages` (for Debian's Pillow), and installs/restarts a **systemd user service** (`deploy/glance.service` → `~/.config/systemd/user/`), so deploys need no sudo. Linger is enabled for the deploying user, so it starts at boot. The unit waits up to 2 min for NTP sync first (the Pi has no RTC) and then starts anyway; `TimeoutStartSec=150` is there because systemd's default start limit (90 s) would end that wait as a failed start. `deploy.sh` also remakes a half-made venv (one without pip), compiles the modules (the sandboxed service can't write `__pycache__`), draws one image with the new code and config before restarting (`render --offline -o /dev/null`; if that fails the old service is left running), and fails if the service isn't running, or has restarted, 12 s after the restart. On this Pi the code takes 4.3 s to load and the pre-start step ~3 s, so a start-up crash is in its restart wait when the check looks.

### Running

mise tasks in `glance-server/` (`mise tasks` lists them; mise creates and activates `.venv`, so plain `python` there is the venv's):

```bash
cd glance-server
mise install && mise run setup   # Python 3.13, .venv with Pillow
mise run test
mise run serve                   # http://localhost:8080/
mise run render                  # one image to glance.png
mise run stops Pasila            # find stop codes
mise run deploy                  # runs the tests first; deploys only if they pass, to $GLANCE_PI
mise run icons                   # rebuild icon PNGs (macOS)
```

Deploy only with `mise run deploy`, not `deploy/deploy.sh` directly, so the tests always run first (verified 2026-11-10: a failing test stops the deploy). The target (`GLANCE_PI=user@host`) lives in `glance-server/mise.local.toml` (git-ignored, layered over `mise.toml` by mise; template `mise.local.toml.example`); without it the deploy stops with a message. Deploys don't copy `mise.local.toml` to the Pi.

On the Pi: `journalctl --user-unit glance -f` (log; `journalctl --user -u` finds no journal files on this Pi), `systemctl --user restart glance`.

### Pi 1 accommodations (revisit on new hardware)

Choices made because the server runs on a Pi 1 (drawing an image takes ~2.2 s there vs ~90 ms on the Mac). Decided 2026-11-10 with the user: keep them, add no switches in advance, and revisit only if the hardware changes.

- **Pre-rendering** (`schedule.Prerendered`, drawn in the refresher loop): not needed on fast hardware, but harmless, since data is polled at :45 either way, so images are equally fresh. On an upgrade, it may be deleted to simplify the code (about 30 lines), or kept.
- **`poll_lead_seconds = 15`**: leaves time to fetch and draw before the device wakes at :02. On fast hardware, ~5 s gives fresher departures (config change only).
- **PNG `compress_level=6`** instead of `optimize=True`: keep (only ~6 % bigger).
- **Debian's `python3-pil` + venv with `--system-site-packages`**, **`Pillow>=9.1`**: keep; simplest on any Debian. (piwheels' ARMv6 wheel lacked system libraries.)
- **systemd user service, NTP wait before start**: not Pi-1-specific; keep (the wait is harmless even with a real-time clock, e.g. a Pi 5).
- To check new hardware: time `render.render` + `render.to_png` there (see how it was measured on 2026-11-10: three renders in a loop with `time.perf_counter`).

## Device firmware (`glance-device/`)

Custom Arduino firmware built with PlatformIO (started 2026-11-10). ESPHome was ruled out: Seeed's ESPHome setup drives the E1001 (`waveshare_epaper`, model `7.50inv2`) in black and white only, and the layout depends on the 4 greys.

- Hardware facts (from Seeed's docs): the E1001 is a XIAO ESP32-S3 (PSRAM) with a UC8179 7.5" panel. Display SPI: SCK 7, MOSI 9, CS 10, DC 11, RST 12, BUSY 13. Logs and flashing go through an on-board USB-to-serial bridge on UART1 (GPIO43 TX / 44 RX), so `Serial1`, not USB CDC. Battery: drive GPIO21 high, read ADC on GPIO1, multiply by 2. Buttons (verified on the device 2026-11-10): **left = GPIO5, middle = GPIO4, right = GPIO3**, pressed = low (as Seeed's Arduino page says; their ESPHome page calling GPIO4 "right" is wrong).
- Libraries: Seeed_GFX (Seeed's TFT_eSPI fork, pinned by commit in `platformio.ini`), selected with `-DBOARD_SCREEN_COMBO=520`; 4 greys via `epaper.initGrayMode(GRAY_LEVEL4)`, a 4-bit 800×480 frame buffer drawn with `TFT_GRAY_0` (black) … `TFT_GRAY_3` (white); `epaper.update()` does a full refresh and wakes/sleeps the panel itself. The server's greys 0/85/170/255 map to levels 0–3 without dithering. (PNG decoding with pngle was tried first and dropped for the `.g2` format; see the status below.)
- Every request carries an `X-Glance-Client: device` header (see Security). If the frame buffer wasn't allocated, the update counts as failed (backoff) instead of crashing.
- Panel power: `epaper.begin()` switches the panel's power on (UC8179 POWER ON in the library's init), and the library switches it off only at the end of a refresh (`update()`, `updataPartial()`). After a failed update there is no refresh, so `panel_off()` does it: `epaper.wake()` then `epaper.sleep()` (the library's `sleep()` does nothing until the panel has been woken once). Found by reading the library 2026-11-11; the current saved was not measured. Tried on the device the same day (server stopped, device reset over serial): the log showed the failed update, `[epd] panel powered down in 977 ms`, then the 30 s retry sleep, and the retry succeeded. So a failed attempt now costs about 1 s more awake. To reset the device from a script without entering the bootloader: open the port with DTR and RTS off, then pulse RTS on for 0.15 s (plain `serial.Serial(port)` did not reset it).
- Wi-Fi and server URL in `include/secrets.h` (git-ignored; template `secrets.h.example`). Use the server's IP, not its `.local` name (mDNS costs awake time).
- Tools via mise (`glance-device/mise.toml`, 2026-11-10): Python 3.13, `uv` and `pipx:platformio` pinned; `mise install` sets them up. Tasks: `mise run build`, `mise run upload`, `mise run monitor` (in `glance-device/`). `platformio.ini` pins `upload_port`/`monitor_port` to `/dev/cu.usbserial-*` (the CH340 bridge); without it PlatformIO auto-picked a Bluetooth port. The earlier `glance-device/.venv` is gone. Building and flashing through mise verified 2026-11-10 (the port pattern found the reTerminal's port). For a scripted log, mise's PlatformIO venv has pyserial: its interpreter is in the first line of `$(mise which pio)`.
- Status 2026-11-10: stages 1–2 done and flashed (USB bridge is a CH340, `/dev/cu.usbserial-*` on the Mac; the device gets its IP by DHCP). The device fetches `/glance.g2` (the server's 2-bit format, 96 KB: 4 px/byte, first pixel in the top bits, 0 = black … 3 = white) and unpacks it straight into Seeed_GFX's 4-bit sprite buffer (`epaper.getPointer()`; 2 px/byte, left pixel in the high nibble, 400-byte rows); PNG decoding with pngle took 2.2 s, this takes ~0.2 s including the download. After the refresh it deep-sleeps for `X-Glance-Sleep` minus the time since the response arrived (so wakes don't drift), and wakes on time to the second (:01). Wi-Fi is switched off before the refresh. The last access point's channel and BSSID are kept in RTC memory, but that barely helps (1.9 s vs 2.0 s): the time is WPA2 authentication + DHCP; a fixed device IP (DHCP reservation + `WiFi.config`) would save the DHCP part. Measured per update: Wi-Fi 1.9 s, download 0.2 s, 4-grey full refresh 6.2 s (the panel; the ESP32 just waits), ~8.7 s awake in all. Flashing works while it sleeps (the USB bridge resets it into the bootloader).
- Buttons and battery (stages 3–4, done 2026-11-10): any button wakes it from deep sleep (ext1, any-low, internal RTC pull-ups with the RTC peripheral domain kept on; a button already down at sleep time is left out of the mask so it can't wake it at once), and that update requests `?refresh=1`. A press while awake (during an update) is caught by a FALLING-edge interrupt and triggers another update with `?refresh=1` right after (a flag in RTC memory, 0.5 s sleep); verified on the device 2026-11-10. Lessons: (1) the interrupt must be IRAM-safe (no `digitalRead()`/`millis()`; that crashed the chip when a press coincided with Wi-Fi flash access); (2) don't read the pin level in the handler: Seeed's driver blocks interrupts for long stretches during the panel refresh, so the handler can run after the button is already released; use falling edges only; (3) the button that woke the device is ignored for its first second (release bounce). Button pins need `rtc_gpio_deinit` at boot after an ext1 wake.
- Battery: read before Wi-Fi starts (the radio's current makes the voltage sag), 8 samples, sent as `?battery_mv=` with every request. The server (`glance/battery.py`) converts with a LiPo curve, keeps the latest report (ignored after 2 h or if implausible), and draws an icon + percentage at the right of the status bar; at ≤ 15 % a "Lataa akku" / "Charge battery" badge appears next to it. Voltage is sent rather than percent so the curve can be tuned without reflashing. Calibration (2026-11-10): a full battery read only 93–94 % on the generic curve (full = 4.20 V), because a real device reads somewhat less when full (the cell settles after charging; the ESP32 ADC through a halving divider reads a bit low). `[battery] full_mv` (`config.toml` default 4200; the device's own value in `config.local.toml`) shifts readings so that maps to 100 %. A shift assumes a constant offset; whether that holds at the low end (where the warning appears) is unverified. Every report is appended to `cache/battery.csv` on the server (`time,mv`; ~600 lines / 18 KB a day), to learn the real discharge curve and battery life on the schedule; the last line restores the level after a server restart. Next step once a full discharge is logged: fit the curve (or at least check the low end) from it.
- Opening the serial port from the Mac resets the device (CH340 DTR/RTS), so a log always starts with "power on / reset". Log everything, not only our `[...]` lines, or crash reports get hidden.
- Failure handling (2026-11-10): consecutive failures (Wi-Fi or server) are counted in RTC memory and retries back off 30 s → 1 → 2 → 5 → 10 → 15 min (cap), back to normal on the first success; a button press retries at once. Timeouts: Wi-Fi 10 s (after a 5 s attempt at the remembered access point, so up to 15 s), HTTP connect 4 s, HTTP 10 s. Verified by stopping the server: a failed attempt costs ~2 s awake ("connection refused" is immediate). Offline mark (chosen with the user over a full-screen notice, 2026-11-10): from the 3rd failure in a row (~1.5 min into an outage) the device draws, once per outage, a white badge with a crossed-out cloud at the right end of the status bar (x 704–800, over the battery level) with a black-and-white partial refresh (~1.1 s), leaving the rest of the last image on the panel; deep sleep erased the image, so it can't be redrawn. Seeed_GFX supports partial refresh on the UC8179 only in 1-bit mode: `deinitGrayMode()`, draw, `epaper.sleep()` first so `updataPartial()` wakes the panel in partial mode. Verified on the device: the badge looks clean and the next successful full refresh replaces it. No text, because the built-in fonts are ASCII-only (no ä/ö).
- Refreshing mark (2026-11-11, asked for by the user: a button refresh takes 10 s or more to show): an update that asks for `?refresh=1` first draws a white badge with two circling arrows in the same spot as the offline mark (`show_mark` draws both; `draw_refresh_icon`, `draw_offline_icon`), with the same black-and-white partial refresh, before the frame buffer is switched to 4 greys. Wi-Fi now starts first (`start_wifi`) and connects while the mark is drawn, so the mark costs no extra time awake (measured: mark on the panel 1.4 s after wake, Wi-Fi up at 2.0 s as before, then the normal 6.2 s 4-grey refresh). Only on refreshes, not timed wakes (it would flash the corner at every wake). If that update fails, the offline mark replaces it at once (not after the 3rd failure), since the mark can't be left up and what was under it is gone. A press during the panel's 6 s refresh still gets no feedback until the follow-up update starts. Tried on the device with two temporary builds (every wake treated as a press; then also a server address that refuses connections): both paths ran as described in the log. The user then pressed a button and found the mark looks good on the panel (the icon was designed in a Pillow mock-up of the same shapes), but sometimes smudgy, sometimes crisp. Likely cause, from reading the driver (not confirmed on the panel): in a partial refresh the UC8179 picks each pixel's drive from an "old" and a "new" image and leaves a pixel alone where they agree; the library's `updataPartial()` sends only the new one, so "old" was whatever the controller's memory held, which after a 4-grey refresh is one half of the grey image's data (dark grey counts as white, light grey as black), so the smoothed edges of the battery level under the mark weren't redrawn. Fix (2026-11-11): `push_mark()` replaces `updataPartial()` for both marks; it runs the library's own sequence (its macros, through two small forwarding functions) and also sends "old" as the inverse of the new image, so every pixel in the mark's area is driven. It bypasses the library's sleep flag on purpose (the library still takes the panel to be asleep, as it has since `begin()`). Flashed and run on the device through a test build (mark in 1.1 s as before, the 4-grey refresh after it normal); the user then tried it and found the mark crisp. A device log of the final firmware the same evening showed a real button wake and two presses while awake (mark each time, Wi-Fi by the remembered access point in 1.95 s, started before the mark) and a normal timed wake (8.7 s awake, as before the change). Listening to that log reset the device once when the port was opened, even with DTR and RTS set off first. The offline mark was tried the same way (a test build that couldn't reach the server and marked the first failure, so the mark went straight over the battery level): the user found it crisp too.
- Wake schedule done 2026-11-10 (see Architecture); verified on the device: it wakes on the 5-minute marks in a 5-minute period. Remaining: maybe a fixed device IP to skip DHCP (~1 s per wake).

## Security (reviewed 2026-11-10 and twice on 2026-11-11)

The second round's fixes (everything dated 2026-11-11 here and above) were flashed and deployed together on 2026-11-11 and checked on the running system: the service started first time with a 2 min 30 s start limit and fresh bytecode for every module, and the device's next wake got its image and had its battery report logged, so the client header works end to end. Not exercised live: a boot without network time, and the deploy script's failure paths.

The third round's fixes were flashed and deployed later on 2026-11-11: the deploy's new pre-check drew an image on the Pi before restarting, the service started first time, and the device's next wakes got their images with battery reports logged.

The threat model is a home network: the server has no login and speaks plain HTTP, by choice (the device is a deep-sleeping ESP32, and the dashboard holds nothing worse than which stops are near home and when the household is up). It must not be reachable from the internet. Within that, a whole-project review led to these measures; keep them when changing the code around them.

- **A request must arrive within 10 s** of connecting (`Handler.timeout` and `_RequestDeadline` in `__main__.py`): idle connections and ones dripping a byte at a time are dropped. A plain socket timeout only limits each read; before, each such connection held a thread for ever.
- **Changes need the `X-Glance-Client` header:** `battery_mv` and `refresh=1` count only in requests carrying it; the firmware and the preview page send it. A web page elsewhere can make a browser at home send a plain GET to the server, but can't add a header without a CORS preflight, which the server never answers. Server and firmware must be updated together: firmware without the header gets images, but its battery reports and button refreshes are ignored.
- **Drawing on demand is shared** (`schedule.Recent`): images outside the pre-drawn window are drawn one at a time and reused for 5 s unless the minute or the data's fetch times change, so a burst of requests costs one drawing, not ~2.5 s of the Pi each. The battery level is deliberately not part of the key (a spoofed `battery_mv` would force redraws); it shows at most 5 s late.
- **Host header check** (`host_allowed`): requests must name the server by IP address, a single-label name, a `.local` name or localhost, or a name listed in `[server] hostnames` (taken as written, so odd names work too); others get 403. This stops DNS rebinding (a web page elsewhere reading the dashboard through a browser at home). A missing Host is allowed (not a browser).
- **Log lines are escaped** (`log_safe`): our `log_message` override had dropped the standard library's escaping of control characters in request lines.
- **Battery log is rate-limited** to one line per 30 s (`battery.LOG_MIN_INTERVAL`); faster reports are shown but not logged, so requests can't fill the disk.
- **Firmware caps `X-Glance-Sleep`** at 25 h (`MAX_SLEEP_S`): the server never asks for more than a day, and a larger value would leave the screen dead for weeks (and overflow past 49 days). Flashed 2026-11-10 (built with the pinned platform); the device booted, fetched, refreshed and slept as before. The cap itself was not exercised on the device (that needs a server sending an oversized value).
- **The systemd unit is sandboxed** (`deploy/glance.service`): of the home directory the service sees only `~/glance-server`, read-only except `cache/` (so not `~/.ssh`); the system is read-only; no new privileges; system-call and address-family filters; `TasksMax=64` bounds threads. All of it works in a user unit without root: tried on the Pi 2026-11-10 in a throwaway `systemd-run --user` unit (config load, drawing, cache write, DNS, HTTPS, listening, `timedatectl` for the NTP wait). `MemoryMax` was left out: this Pi delegates only the cpu and pids controllers to user units, so it would do nothing. `deploy.sh` creates `cache/` first, because the unit fails to start if a bound path is missing; a `[cache] dir` elsewhere needs its own `BindPaths`. Deployed 2026-11-10 and checked on the running service: `NoNewPrivs` 1, seccomp filter on, `/home` read-only with only `cache/` writable; a request by IP or `.local` name gets 200, a foreign Host 403; a second request 1 s after a 2.4 s drawing took 0.2 s (shared).
- **Pinned builds:** `platform = espressif32@8.0.0` in `platformio.ini`, next to the commit-pinned Seeed_GFX. `Pillow>=9.1` stays a range on purpose: the Pi uses Debian's Pillow, and an exact pin would make pip try to replace it.
- **Tests are isolated** (`isolated_config` in `tests/test_glance.py`): they use `config.toml` alone (`config.load(local_overrides=False)`), a temporary cache folder and no network (checked 2026-11-11 by running them with outside connections blocked, in three other time zones, and with `GLANCE_DIGITRANSIT_KEY` set). Two leftovers were fixed the same day: a test that failed 10–27 s before a night quarter hour, and one that read the environment variable. Before, they read `config.local.toml`, fetched from FMI and rewrote the real cache, so a local schedule could fail a test and block the deploy.
- **Secrets:** none in the repository (checked against the real values). `config.local.toml` and `secrets.h` are mode 600 on the Mac; `deploy.sh` writes the Pi's copy 600.

Config values are validated at startup (intervals, `poll_lead_seconds` under a minute, times as HH:MM, a non-negative wake offset; unquoted stop codes become text), so a typo stops the deploy's pre-check instead of breaking every drawing later. Left as is from the third review: upstream fetches have no overall deadline (their socket timeouts and the 4 s request wait bound the effect).

Accepted, not fixed: any device on the home network can view the dashboard, send a false `battery_mv` or trigger `?refresh=1` by adding the client header itself (bounded by the rate limits above), hold the service's 64 threads busy, and something answering at the server's address could feed the device its own image. Fixing those needs a shared token or TLS on both sides; a token over plain HTTP adds little, and it was left out to keep the firmware trivial. The Wi-Fi password is readable from the device's flash over USB (flash encryption burns eFuses irreversibly, so not done): put the device on a guest/IoT network if that matters.

## Screen layout (settled with the user, tested on the real panel)

- 30 px black status bar: date + time on the left; on the right only a warning badge when data is old or missing. (It used to show "Updated HH:MM"; removed 2026-11-10 with the user, since data fetched just before the minute made it read one minute behind the clock.)
- Below it, a 6×3 grid (cells ≈133×150 px), no grid lines.
- **Row 1:** current weather 2×1: icon, big temperature with today's high/low stacked right after it (high in black over low in dark grey, no arrows; the temperature shrinks rather than overlap them), condition text, then "Tuntuu kuin 3°" / "Feels like 3°" (FMI's FeelsLike) and wind (layout changed with the user 2026-11-10; high/low used to be on the bottom line) + hourly forecast 4×1 with 12 compact columns in the style of a phone weather app: temperature, icon, precipitation %, hour. The percentage is drawn for every hour, 0 % included (a gap looked like an error; user's call 2026-11-10), rounded to 10 %, in the language's style ("60 %" in Finnish).
- **Rows 2–3:** three stop widgets, 2×2 each, headed by HSL's mode pictogram(s) and the stop name, showing the next 8 departures: route badge (filled black = tram, outlined = bus, light grey fill with black outline = HSL trunk bus/runkolinja, orange at HSL; chosen with the user 2026-11-10 over dark grey, which is too close to black on the panel), destination, minutes. Minutes in black = realtime, dark grey = scheduled only.
- Electricity prices were dropped for now.

## Design rules learned on the device

- Only four grey levels; antialiasing must be snapped to them. Light grey (170) works for large fills (sun icon), not for small text.
- Icons for e-paper need bold strokes: hairlines and coloured details (FMI's yellow lightning, blue snowflakes) fade to light grey or vanish once snapped to four greys, especially at the 36 px hourly size.
- Route numbers and minutes are what people read first; when space is tight, shrink the destination text, not those.
- Long names: shrink to a minimum size, then truncate with "…".
- Temperatures use a real minus sign (−3°) and must never overlap the icon.
